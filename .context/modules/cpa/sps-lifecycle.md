# CPA Lifecycle Job Stored Procedures

This document covers CPA calculation job stored procedures that manage the player CPA lifecycle from Active qualification through Approval/Payment.

**Execution Flow**: Daily SQL Server Agent job (06:00 GMT+8) → Task_Aff_CPACalculation_Job → Sequential sub-steps

---

## 📋 Summary Table

| SP Name | Purpose | Phase | Main Tables Written |
|---------|---------|-------|---------------------|
| Task_Aff_CPACalculation_Job | Orchestrates sequential execution of CPA sub-steps for a day | Wrapper | CPAJobLog (+ delegates) |
| Task_Aff_CPAResetIsAbnormal | Resets previously marked abnormal players back to Pending if tags no longer abnormal | Pre-Active | MemberCPA |
| Task_Aff_CPAActivePeriod | Qualifies players for Active period (creates / updates MemberCPA, Tier & Product details, archives EOL) | Active | MemberCPA, MemberCPATier, MemberCPAProduct, MemberCPA_EOL |
| Task_Aff_CPAHoldingPeriod | Evaluates Holding bet ticket condition and updates status / holding dates | Holding | MemberCPA |
| Task_Aff_CPAMarkIsAbnormal | Marks players as abnormal (StatusId=4) based on tag rules | Post-Holding (filter) | MemberCPA |
| Task_Aff_CPACheckRedeposit | Checks redeposit condition inside monitoring window, sets IsRedeposit flag | Monitoring | MemberCPA |
| Task_Aff_CPAPaymentSchedule | Builds per-affiliate schedule row (rptAffiliateCPA) from qualified holding completions | Payment Prep | rptAffiliateCPA |
| Task_Aff_CPAApprovalPeriod | Creates AffTrans (financial) and sets StatusId=3 (Paid); applies quota rules | Approval | AffTrans, MemberCPA |
| Task_Aff_UpdateDealSchedule | Advances NextBillingDate of deals of given Type | Post-Approval | DealBillingSchedule |

## StatusId Legend (MemberCPA)

| StatusId | Name | Description |
|----------|------|-------------|
| 0 | Pending | Active period met, awaiting holding phase |
| 1 | InEligible | Holding phase failed (deadline expired without meeting ticket requirement) |
| 2 | Eligible | Holding phase met, awaiting payment window / redeposit monitoring |
| 3 | Settled / Paid | Payment approved and AffTrans created |
| 4 | Abnormal | Excluded due to abnormal tags (fraud/risk markers) |
| 5 | Quota Exceeded | Qualified but not paid (affiliate quota limit reached) |
| 6 | Redeposit Failed | Monitoring window expired without meeting redeposit threshold |

## Task_Aff_CPAActivePeriod

**PURPOSE**: Qualify players for Active period (FDM/deposit/turnover thresholds), assign CPA tiers, calculate amounts, handle recalculation for existing players and archive expired non-qualified players.

**BUSINESS RULE**: Player qualifies for CPA Active period when meeting tier conditions (MinFDM AND/OR MinTotalDeposit AND/OR MinTO) within ActiveDays window from registration. Existing qualified players are recalculated if conditions changed.

**PARAMETERS**:

| Name | Type | Required | Default | Description |
|------|------|----------|---------|-------------|
| @CPADate | DATE | Yes | - | Execution date (determines Active window boundaries) |
| @ErrCode | INT | No | OUTPUT | Error code (0=success, 100=null date) |
| @ErrMsg | NVARCHAR(8000) | No | OUTPUT | Error message text |

**TEMP TABLES**:

| Table | Columns | Purpose |
|-------|---------|---------|
| #GroupCountry | GroupId, CountryCode | Currency-country mapping per CPA group |
| #GroupCurrency | GroupId, ExchangeId | Exchange rate reference per group |
| #DealSetting | GroupId, GroupProductId, TierId, MinFDM, MinTotalDeposit, MinTO, CPAAmount, MaxTier | Active tier settings with thresholds |
| #PlayerDeal | MemberCPA_ID, CustId, AffId, GroupId, OldActiveQualifiedDate, ActiveDeadline, HoldingDeadline | Player baseline with deadlines |
| #PlayerProductSummary | CustId, GroupProductId, ProductId, TotalDeposit, Turnover, BetCount, FDM | Aggregated player activity per product |
| #PlayerProductQualification | CustId, GroupId, GroupProductId, TierId, CPAAmount, TotalDeposit, Turnover, FDM | Tier-matched qualified players |

**READS FROM**:

- MemberCPA (existing qualified players for recalculation)
- MemberInfo (CustId, AffId, RegisteredDate, FDM, TagList, CountryCode)
- CPAGroupSetting (ActiveDays, HoldingDays, target countries, current ToDate=9999-12-31)
- CPATierSetting (MinFDM, MinTotalDeposit, MinTO, CPAAmount per tier, current ToDate=9999-12-31)
- CPAProductSetting (product mapping per tier)
- rptMemberDaily (aggregated deposit/turnover/bet history)
- bodb_12B.dbo.DepositInfo (FDM verification)
- Exchange, TargetCountry (currency normalization)

**WRITES TO**:

| Table | Operation | Key Columns | Condition |
|-------|-----------|-------------|-----------|
| MemberCPA | DELETE | MemberCPA_ID | Group changed, country excluded, or no longer qualifying |
| MemberCPA | MERGE (UPDATE/INSERT) | StatusId=0, ActiveQualifiedDate, TotalDeposit, Turnover, FDM, CPAAmount, Deadlines | Qualified players (new or recalculated) |
| MemberCPA_EOL | INSERT | MemberCPA_ID, CustId, AffId, ArchiveReason, CPADate | Expired players (deadline passed without qualification) |
| MemberCPATier | DELETE + INSERT | MemberCPA_ID, GroupProductId, TierId, CPAAmount, Turnover | Rebuild tier details |
| MemberCPAProduct | DELETE + INSERT | MemberCPA_ID, GroupProductId, ProductId, Turnover, BetCount | Rebuild product details |

**LOGIC FLOW**:

```sql
-- High-level pseudocode
1. Load base currency & system settings
2. Build #GroupCurrency and #GroupCountry mappings
3. Load #DealSetting (active CPATierSetting with MaxTier per group/product)
4. Load existing MemberCPA players (#PlayerDeal) in StatusId IN (0,1) within recalculation window
5. Aggregate historical Active period activity into #PlayerProductSummary from rptMemberDaily
6. Tier match into #PlayerProductQualification using threshold comparisons; keep highest tier
7. DELETE obsolete MemberCPA rows (group change, country exclusion, disqualification)
8. MERGE qualifications into MemberCPA (UPDATE existing / INSERT new)
9. Archive expired non-qualified players into MemberCPA_EOL
10. Rebuild MemberCPATier & MemberCPAProduct detail tables
11. Process new players (not yet in MemberCPA) using same steps with current window
```

**DECISION TREE**:

```text
Registered Player → In MemberCPA?
  No → New Path (qualify & insert)
  Yes → Recalc Path
    Group Changed? → Delete + Archive → End
    Country Excluded? → Delete + Archive → End
    Aggregate Activity → Meets Tier? → No → Delete + Archive | Yes → MERGE/UPDATE → Rebuild Detail Tables
```

**SIDE EFFECTS**:

- Cascading deletes remove tier/product rows.
- Exchange rate function calls per player-product row.
- Archive table grows daily (retention strategy required later).

**EDGE CASES**:

- NULL @CPADate → @ErrCode=100 early return.
- Group or Country changes mid-cycle cause deletion + potential future requalification.
- Multiple product tiers per player supported.
- FDM re-evaluated each run using latest MemberInfo.
- Deadline exceeded triggers archival.

**IDEMPOTENT**: Yes (recalculation safe; DELETE+INSERT pattern ensures consistent state).

**ERRORS**:

| @ErrCode | Meaning |
|----------|---------|
| 0 | Success |
| 100 | @CPADate NULL |

**PERFORMANCE NOTES**:

- Processes 10K–100K+ players.
- Critical indexes: MemberCPA(StatusId, RegisteredDate, GroupId, AffId), rptMemberDaily(CustId, WinlostDate, GroupProductId), CPATierSetting(GroupId, ToDate).
- Temp table indexing (CustId, GroupId, GroupProductId) reduces join costs.
- Expected runtime 5–15 minutes.

**SAMPLE I/O**:

- New qualification → INSERT MemberCPA with StatusId=0 & deadlines.
- Group change → DELETE old row & archive reason 'GroupChanged'.
- Deadline expired without activity → Archive with reason 'DeadlineExpired'.

**DEPENDENCIES**:

- Called by: Task_Aff_CPACalculation_Job (step sequencing)
- Calls: Aff_f_ExchangeRate_Sel, (potential helper Aff_f_GroupProduct)
- Requires current open CPAGroupSetting / CPATierSetting / CPAProductSetting rows.

## Task_Aff_CPAHoldingPeriod

**PURPOSE**: Evaluate Holding phase bet ticket requirement for players who passed Active phase (StatusId=0), transition to Eligible (StatusId=2) if met or InEligible (StatusId=1) if deadline expired.

**BUSINESS RULE**: After Active qualification, player must place HoldingTickets bets within HoldingDays window. HoldingTickets=0 ⇒ immediate StatusId=2.

**PARAMETERS**:

| Name | Type | Required | Default | Description |
|------|------|----------|---------|-------------|
| @CPADate | DATE | Yes | - | Execution date (holding window evaluation) |
| @ErrCode | INT | No | OUTPUT | Error code (0=success, 100=null date) |
| @ErrMsg | NVARCHAR(MAX) | No | OUTPUT | Error message text |

**TEMP TABLES**:

| Table | Columns | Purpose |
|-------|---------|---------|
| #Member | MemberCPA_ID, CustId, ActiveQualifiedDate, OldHoldingQualifiedDate, HoldingDays, HoldingTickets, HoldingDeadline | Candidate StatusId=0 members |
| #BetTickets | CustId, BetTickets_Old, BetTickets_New, TotalBetTickets | Aggregated bet counts (old qualified period + current window) |

**READS FROM**:

- MemberCPA (StatusId=0, ActiveQualifiedDate)
- CPAGroupSetting (HoldingDays, HoldingTickets)
- rptMemberDaily (BetCount per CustId & day)

**WRITES TO**:

| Table | Operation | Columns |
|-------|-----------|---------|
| MemberCPA | UPDATE | StatusId, HoldingQualifiedDate, HoldingBetTickets, HoldingExpiredDate, UpdatedDate |

**LOGIC FLOW**:
```sql
1. Load candidates with StatusId=0 and ActiveQualifiedDate in valid range.
2. Compute HoldingDeadline = ActiveQualifiedDate + HoldingDays.
3. Aggregate BetCount into #BetTickets (old + new segments).
4. Derive HoldingQualifiedDate & StatusId based on TotalBetTickets vs HoldingTickets & deadline.
5. Persist updates to MemberCPA.
```

**DECISION TREE**:
```text
StatusId=0 → HoldingTickets=0? → Yes → StatusId=2
  No → TotalBetTickets >= HoldingTickets? → Yes → StatusId=2
       No → Deadline passed? → Yes → StatusId=1 | No → Stay StatusId=0
```

**SIDE EFFECTS**:

- StatusId=1 rows become terminal for lifecycle.
- HoldingQualifiedDate set once; not recalculated.

**EDGE CASES**:

- NULL @CPADate → @ErrCode=100.
- HoldingTickets=0 fast-track eligibility.
- Previous partial qualification retains old HoldingQualifiedDate if already met.

**IDEMPOTENT**: Yes (re-run recomputes counts; stable terminal transitions).

**ERRORS**:

| @ErrCode | Meaning |
|----------|---------|
| 0 | Success |
| 100 | @CPADate NULL |

**PERFORMANCE NOTES**:

- Moderate volume subset (only StatusId=0).
- Runtime ~1–3 minutes with proper indexes.

**SAMPLE I/O**:

- Meets holding → StatusId=2, HoldingQualifiedDate=run date.
- Deadline expired → StatusId=1, HoldingExpiredDate set.
- No holding requirement → Immediate StatusId=2.

**DEPENDENCIES**:

- Called by: Task_Aff_CPACalculation_Job
- Reads CPAGroupSetting for open rows.

## Task_Aff_CPACalculation_Job

**PURPOSE**: Daily wrapper orchestrating CPA lifecycle sub-steps in ordered sequence (Reset Abnormal → Active → Holding → Mark Abnormal → Redeposit Check → Payment Schedule → Approval (payout) → Deal Schedule advance).

**BUSINESS RULE**: Executes one specific step when @Step provided (1–8) or all steps when @Step=0. Each nested SP logs outcome to `CPAJobLog`; failure in a step raises error and halts subsequent steps.

**PARAMETERS**:

| Name | Type | Required | Default | Description |
|------|------|----------|---------|-------------|
| @Step | INT | No | 0 | 0 = run all; otherwise run only specified step (1–8) |
| @Date | DATE | No | NULL | CPA processing date; defaults to yesterday GMT+8 |

**READS FROM**:

- System time (GETUTCDATE()) for deriving @Date
- CPAJobLog (for MAX(LogID) retention trimming)

**WRITES TO**:

| Table | Operation | Columns |
|-------|-----------|---------|
| CPAJobLog | INSERT | StepName, ExecDate, StartTime, EndTime, Status, ErrorMessage |
| CPAJobLog | DELETE | LogID (retention prune > 2000) |

**LOGIC FLOW**:

```sql
1. Derive @Date (yesterday GMT+8 if NULL)
2. For each step s in ordered list (1..8):
  IF @Step IN (0, s) THEN
    Start timer
    EXEC sub-proc for step
    Insert CPAJobLog row (Success/Failed + error message)
    IF failed → RAISERROR to abort wrapper
3. Trim CPAJobLog (DELETE LogID < MAX(LogID) - 2000)
```

**STEP SEQUENCE**:
1 Reset IsAbnormal
2 Active Period
3 Holding Period
4 Mark IsAbnormal
5 Check Redeposit
6 Payment Schedule build/update
7 Approval Period (payout & status transitions)
8 Update Deal Schedule (advance NextBillingDate)

**DECISION TREE**:

```text
@Step = 0? → Yes → Run all steps sequentially
         No → Run only matching step
Each step result → Success? → Continue | Failure? → RAISERROR & stop
After completion → Trim CPAJobLog
```

**SIDE EFFECTS**:

- Centralized failure propagation; partial completion if a mid-step fails.
- Logs accumulate (bounded to 2000 rows).

**EDGE CASES**:

- Missing @Date handled automatically.
- Invalid @Step (>8) silently results in no nested execution (only log trimming).

**IDEMPOTENT**: Partially — repeating same @Date re-executes sub-steps which themselves are idempotent or safely recalculative (see individual sections).

**ERRORS**:

| Source Step | Failure Handling |
|-------------|------------------|
| Any nested SP | RAISERROR with step-specific message; wrapper halts |

**PERFORMANCE NOTES**:

- Light overhead: timing + 8 EXEC calls.
- Dominated by nested procedures' cost.

**SAMPLE I/O**:

- Input: @Step=2, @Date='2025-11-19' → Executes only Active Period; logs 1 row.
- Input: @Step=0 → Executes full chain; 8 log rows + trimming.

**DEPENDENCIES**:

- Calls: Task_Aff_CPAResetIsAbnormal, Task_Aff_CPAActivePeriod, Task_Aff_CPAHoldingPeriod, Task_Aff_CPAMarkIsAbnormal, Task_Aff_CPACheckRedeposit, Task_Aff_CPAPaymentSchedule, Task_Aff_CPAApprovalPeriod, Task_Aff_UpdateDealSchedule.
- Relies on CPAJobLog structure (LogID identity assumed).

## Task_Aff_CPAResetIsAbnormal

**PURPOSE**: Revert previously flagged abnormal players (StatusId=4) to Pending (StatusId=0) if their current tag set no longer contains abnormal tags within the recalculation registration window.

**BUSINESS RULE**: A StatusId=4 record is reset when NO abnormal tags remain; description cleared; UpdatedDate timezone-adjusted.

**PARAMETERS**:

| Name | Type | Required | Description |
|------|------|----------|-------------|
| @CPADate | DATE | Yes | Processing reference date (window anchor) |
| @ErrCode | INT | OUTPUT | 0 success; 100 null date |
| @ErrMsg | NVARCHAR(8000) | OUTPUT | Error text or NULL |

**READS FROM**:
- SystemSettings (TimeZone)
- MemberCPA (StatusId=4 rows)
- MemberInfo (CustId, TagList, RegisteredDate)
- CPAGroupSetting (ActiveDays, HoldingDays current open row)
- bodb_12B.dbo.Tag (IsAbnormal flag)

**WRITES TO**:
| Table | Operation | Columns |
|-------|-----------|---------|
| MemberCPA | UPDATE | StatusId, Description, UpdatedDate |

**LOGIC FLOW**:

```sql
1. Validate @CPADate
2. Compute registration window start based on ActiveDays+HoldingDays
3. UPDATE MemberCPA SET StatusId=0, Description='' WHERE StatusId=4 AND within window AND NOT EXISTS abnormal tag
4. Set @ErrCode=0
```

**DECISION TREE**:

```text
@CPADate NULL? → Err 100
Else → StatusId=4 & in window? → Abnormal tags exist? → Yes: skip | No: reset to Pending
```

**SIDE EFFECTS**:

- Resets allow players to re-enter Active/Holding evaluation.

**EDGE CASES**:

- Empty TagList always considered non-abnormal ⇒ resets.
- Tag changes between runs immediately reflected.

**IDEMPOTENT**: Yes — second run finds no qualifying StatusId=4 rows (already reset).

**ERRORS**:
| Code | Meaning |
|------|---------|
| 0 | Success |
| 100 | @CPADate NULL |

**PERFORMANCE NOTES**:

- Narrow UPDATE; filtered set (only StatusId=4).
- Tag split uses STRING_SPLIT — ensure appropriate compatibility level.

**SAMPLE I/O**:

- Player with previous abnormal tag removed overnight → reset to Pending.

**DEPENDENCIES**:

- Requires open CPAGroupSetting row (ToDate=9999-12-31).

## Task_Aff_CPAMarkIsAbnormal

**PURPOSE**: Mark players as abnormal (StatusId=4) when any current tag is abnormal, aggregating abnormal tag names into Description.

**BUSINESS RULE**: Only affects rows not already terminal (excludes StatusId IN (3,4,5,6)). Description set to comma-separated abnormal tag names.

**PARAMETERS**:

| Name | Type | Required | Description |
|------|------|----------|-------------|
| @CPADate | DATE | Yes | Processing date |
| @ErrCode | INT | OUTPUT | 0 success; 100 null date |
| @ErrMsg | NVARCHAR(8000) | OUTPUT | Error text or NULL |

**READS FROM**:
- SystemSettings (TimeZone)
- MemberCPA (non-terminal statuses)
- MemberInfo (TagList, RegisteredDate)
- CPAGroupSetting (window calculation)
- bodb_12B.dbo.Tag (IsAbnormal, TagName)

**WRITES TO**:
| Table | Operation | Columns |
|-------|-----------|---------|
| MemberCPA | UPDATE | StatusId=4, Description=aggregated TagName, UpdatedDate |

**LOGIC FLOW**:

```sql
1. Validate @CPADate
2. Registration window filter same as reset SP
3. Identify members with any abnormal tag (EXISTS)
4. CROSS APPLY STRING_AGG abnormal tag names
5. UPDATE StatusId=4, Description=Tag list
6. @ErrCode=0
```

**DECISION TREE**:

```text
@CPADate NULL? → Err 100
Else → status not terminal & in window & abnormal tags exist → Mark abnormal
```

**SIDE EFFECTS**:

- Excludes players from subsequent payment phases.

**EDGE CASES**:

- Multiple abnormal tags aggregated.
- Player already abnormal (StatusId=4) unchanged.

**IDEMPOTENT**: Yes — repeated runs preserve StatusId=4 and Description.

**ERRORS**:
| Code | Meaning |
|------|---------|
| 0 | Success |
| 100 | @CPADate NULL |

**PERFORMANCE NOTES**:

- STRING_AGG per qualifying row — limited by abnormal tag count.

**SAMPLE I/O**:

- Player with TagList '12,45' where tag 45 abnormal → StatusId=4, Description='Risk, Fraud'.

**DEPENDENCIES**:

- Consumes same CPAGroupSetting window logic; relies on Tag metadata.

## Task_Aff_CPACheckRedeposit

**PURPOSE**: During monitoring window, evaluate redeposit condition for Eligible (StatusId=2) players, setting IsRedeposit=1 when cumulative post-first-deposit amount exceeds initial FDM baseline.

**BUSINESS RULE**: Only members where @CPADate within [HoldingQualifiedDate, ExpiredRedepositDate]; FDM normalized to base currency; total deposit (excluding product segmentation) compared to FDM.

**PARAMETERS**:

| Name | Type | Required | Description |
|------|------|----------|-------------|
| @CPADate | DATE | Yes | Evaluation date |
| @ErrCode | INT | OUTPUT | 0 success; 100 null date |
| @ErrMsg | NVARCHAR(MAX) | OUTPUT | Error text |

**TEMP TABLES**:

| Table | Purpose |
|-------|---------|
| #MembersToCheck | Candidate StatusId=2 members with monitoring window and baseline dates |
| #RedepositResults | Computed cumulative redeposit totals & flag |

**READS FROM**:
- SystemSettings (AffCurrency, TimeZone)
- TpExchange / Aff_f_ExchangeRate_Sel (currency conversion)
- MemberCPA (StatusId=2 window rows)
- MemberInfo (FirstDepositAmount, Currency, FirstDepositDate)
- rptMemberDaily (deposit aggregation) — ProductId=-1 filter

**WRITES TO**:
| Table | Operation | Columns |
|-------|-----------|---------|
| MemberCPA | UPDATE | IsRedeposit=1, UpdatedDate |

**LOGIC FLOW**:

```sql
1. Validate @CPADate
2. Load candidates (StatusId=2, monitoring window active, IsRedeposit=0)
3. Normalize FDM to base currency
4. Aggregate deposits between FirstDepositDate and MIN(@CPADate, ExpiredRedepositDate)
5. Compare > FDM → HasRedeposit flag
6. UPDATE MemberCPA for HasRedeposit=1 rows
7. Cleanup temp tables
```

**DECISION TREE**:

```text
In monitoring window & IsRedeposit=0 → CumulativeDeposits > FDM? → Yes: set IsRedeposit | No: remain 0
```

**SIDE EFFECTS**:

- Sets flag used in payment schedule qualification.

**EDGE CASES**:

- ExpiredRedepositDate NULL → member skipped (no redeposit requirement).
- Currency conversion fallback Rate=1 when missing exchange.

**IDEMPOTENT**: Yes — once IsRedeposit=1 it stays; re-run doesn't double-update others.

**ERRORS**:
| Code | Meaning |
|------|---------|
| 0 | Success |
| 100 | @CPADate NULL |

**PERFORMANCE NOTES**:

- Moderate; limited to monitoring subset.
- CROSS APPLY function per daily row; window bounded.

**SAMPLE I/O**:

- Player FDM=100, cumulative redeposit=150 → IsRedeposit set to 1.

**DEPENDENCIES**:

- Exchange rate function; relies on ProductId=-1 deposits being recorded.

## Task_Aff_CPAPaymentSchedule

**PURPOSE**: Build or update per-affiliate CPA payment schedule rows (rptAffiliateCPA) categorizing each schedule into Monitoring / Qualified / Not Qualified / Empty based on redeposit progress and time window; also updates older monitoring rows.

**BUSINESS RULE**: At billing date (DealBillingSchedule.NextBillingDate=@CPADate) create a schedule record summarizing eligible players and redeposit status; old Monitoring rows recalculated and transitioned.

**PARAMETERS**:

| @ErrCode | INT | OUTPUT | 0 success; 100 null date |

**TEMP TABLES**:

| Table | Purpose |
|-------|---------|
| #EligibleGroupsWithAff | Billing-date group-affiliate pairs & redeposit settings |

| #OldMonitoringGroups | Prior cycles still monitoring |
| #UpdatedMonitoringSchedule | Recomputed monitoring outcomes |
| #NewCPASchedule | New schedule rows (including empty groups) |

**READS FROM**:
- SystemSettings (TimeZone)
- DealBillingSchedule (NextBillingDate)
- CPAGroupSetting (RedepositDays, Rate)
- Schedule (interval calculation)
- AffGroupHistory (active affiliation)
- CommGroup (IsDeleted exclusion)

**WRITES TO**:
| Table | Operation | Columns |
|-------|-----------|---------|
| rptAffiliateCPA | UPDATE | Status, ExpiredRedepositDate, counts, EstimateAmount, IsProcessed, UpdatedDate |
| rptAffiliateCPA | INSERT | StartSchedule, EndSchedule, AffId, GroupId, Status, ExpiredRedepositDate, totals, IsProcessed, UpdatedDate |

**LOGIC FLOW**:

```sql
1. Validate @CPADate
2. Load eligible billing groups & affiliates
3. Load qualified members for current cycle
4. Load old monitoring rows needing update
5. Aggregate old monitoring metrics → classify status transitions
6. Compute new cycle aggregates (include empty groups)
7. Insert new schedule rows
8. Update existing monitoring rows
9. Set success message
```

**STATUS RULES (new / old)**:
| Condition | Status |
|-----------|--------|
| No members | Empty |
| No redeposit requirement | Qualified |
| Redeposit in progress & below required & window active | Monitoring |
| Redeposit met | Qualified |
| Window elapsed & requirement unmet | Not Qualified |

**DECISION TREE**:

```text
Group billing today? → Yes → Aggregate players → Apply status rules → Insert/Update schedule
Old Monitoring row? → Re-aggregate → Transition status
```

**SIDE EFFECTS**:

- Multiple inserts per day (one per group-aff pair) — growth of rptAffiliateCPA.
- Some rows flagged IsProcessed=1 immediately if Empty.

**EDGE CASES**:

- RedepositDays NULL ⇒ treated as no redeposit requirement (Qualified).
- RedepositRate 0 ⇒ RequiredRedepositPlayers=0 ⇒ Qualified.

**IDEMPOTENT**: No (reinserting same day duplicates if run twice). Wrapper job should control single execution per date.

**ERRORS**:
| Code | Meaning |
|------|---------|
| 0 | Success |
| 100 | @CPADate NULL |

**PERFORMANCE NOTES**:

- Aggregations grouped by AffId/GroupId; ensure indexes on rptAffiliateCPA(AffId, GroupId, EndSchedule).
- Temp tables sized by active deals × affiliates.

**SAMPLE I/O**:

- Affiliate A group G: 10 eligible, required redeposit=3, current redeposit=1 (window active) → Monitoring.

**DEPENDENCIES**:

- Drives later Approval phase (Task_Aff_CPAApprovalPeriod).

## Task_Aff_CPAApprovalPeriod

**PURPOSE**: Finalize CPA payouts: apply quota rules, create AffTrans (main CPA earning), update MemberCPA statuses to Paid (3) or Redeposit Failed (6), mark schedule records processed; includes robust rollback on error.

**BUSINESS RULE**: Only schedules with Status='Qualified' and IsProcessed=0 produce payouts; quotas restrict number of payments (StatusId set to 5 for exceeded). Not Qualified schedules mark members StatusId=6. Sub-commission logic scaffolded (commented for future extension).

**PARAMETERS**:

**TEMP TABLES (key)**:

| Table | Purpose |

**READS FROM**:
- SystemSettings (AffCurrency, TimeZone)

- MemberInfo (FirstDepositDate)

**WRITES TO**:
| Table | Operation | Columns |
|-------|-----------|---------|

**LOGIC FLOW**:

```sql

6. Insert main CPA AffTrans grouped by affiliate
7. Update paid members (StatusId=3) linking RefId
8. Update failing members (StatusId=6) & quota exceeded (5 already set)
9. Update schedules (ApprovedAmount for qualified, processed flags)
10. On error: rollback via backups + delete created transactions
```

**DECISION TREE**:

```text
Schedule Qualified & IsProcessed=0? → Yes → Members → Apply quota → Payout → Mark processed
Schedule Not Qualified & IsProcessed=0? → Mark members Failed (6) → Mark processed
Quota unlimited? → No quota filtering | Quota limited → ROW_NUMBER ordering selects first Remain
Error occurs? → Manual rollback of all updates
```

**SIDE EFFECTS**:

- Sets terminal statuses (3,5,6) impacting future lifecycle runs.
- Creates financial transaction entries.
- Manual rollback ensures consistency without explicit TRAN.

**EDGE CASES**:

- Quota=0 ⇒ unlimited (Remain NULL).
- All members quota-exceeded ⇒ schedule ApprovedAmount=0.
- Sub-commission currently disabled (future reactivation possible).

**IDEMPOTENT**: No — second execution would duplicate payouts unless wrapper prevents re-run (IsProcessed flag safeguards typical duplication).

**ERRORS**:
| Code | Meaning |
|------|---------|
| 0 | Success |
| 100 | @CPADate NULL |
| Other | SQL error number (captured in CATCH) |

**PERFORMANCE NOTES**:

- Heavy: multi-temp tables & grouping; quota ROW_NUMBER ordering requires proper indexing on MemberCPA.
- No explicit transaction — relies on fast rollback via backups.

**SAMPLE I/O**:

- Qualified schedule with 25 members, quota 20 → 20 paid (StatusId=3), 5 exceeded (StatusId=5).
- Not Qualified schedule → all 12 members set StatusId=6.

**DEPENDENCIES**:

- Requires prior PaymentSchedule step completion.
- Affects downstream reporting (AffTrans, MemberCPA status metrics).

## Task_Aff_UpdateDealSchedule

**PURPOSE**: Advance `DealBillingSchedule.NextBillingDate` for CPA deals after Approval phase using interval rules (monthly +4 days offset or day interval).

**BUSINESS RULE**: For schedules matching @Date and @Type, set next date according to Schedule.IntervalType & IntervalValue; monthly schedules advance to EOMONTH + 4 days of future month.

**PARAMETERS**:

| Name | Type | Required | Description |
|------|------|----------|-------------|
| @Date | DATE | Yes | Current billing date being rolled forward |
| @Type | VARCHAR(100) | No | Deal type filter (CPA expected) |
| @ErrCode | INT | OUTPUT | 0 success; 100 null date |
| @ErrMsg | NVARCHAR(MAX) | OUTPUT | Result / error message |

**READS FROM**:

- DealBillingSchedule (current NextBillingDate)
- Schedule (IntervalType, IntervalValue)
- CPAGroupSetting (ensures group is CPA-capable ToDate=9999-12-31)

**WRITES TO**:

| Table | Operation | Columns |
|-------|-----------|---------|
| DealBillingSchedule | UPDATE | NextBillingDate |

**LOGIC FLOW**:

```sql
1. Validate @Date
2. UPDATE schedules WHERE NextBillingDate=@Date AND Type=@Type
  SET NextBillingDate = CASE IntervalType WHEN MONTH THEN EOMONTH(@Date, IntervalValue-1)+4 ELSE DATEADD(DAY, IntervalValue, @Date)
3. Return updated count in message
```

**DECISION TREE**:

```text
@Date NULL? → Err 100
Else → For each matching schedule apply date rule → Done
```

**SIDE EFFECTS**:

- Drives future PaymentSchedule generation timing.

**EDGE CASES**:

- IntervalValue=1 monthly → next = EOMONTH(current)+4 days.
- Non-month intervals rely on simple day addition.

**IDEMPOTENT**: No — repeating same @Date would push schedule multiple cycles ahead.

**ERRORS**:
| Code | Meaning |
|------|---------|
| 0 | Success |
| 100 | @Date NULL |
| Other | SQL error number (TRY/CATCH) |

**PERFORMANCE NOTES**:

- Single set-based UPDATE; row count typically small.

**SAMPLE I/O**:

- Schedule monthly interval=1, @Date=2025-11-20 → NextBillingDate=2025-11-30 +4d = 2025-12-04.

**DEPENDENCIES**:

- Executed after Approval to prepare next cycle.
