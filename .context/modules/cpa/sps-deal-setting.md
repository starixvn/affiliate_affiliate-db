## Shared Concepts

**Deal Types**:
* 1 = Revenue Share
* 3 = CPA
* 4 = Hybrid (Revenue + CPA)

**Versioning (CPA only)**: 
* Rows have FromDate / ToDate with open-ended ToDate = 9999-12-31
* Updates either:
  - (a) Same-day replacement: DELETE + INSERT with same FromDate=ActionDate
  - (b) Close previous: UPDATE ToDate to yesterday, INSERT new open row with FromDate=ActionDate

**Infinity Constants**: 
* MinAmount negative infinity = -100000000000
* MaxAmount positive infinity = 100000000000
* MaxQM = 1000000000
* CPA max caps = 100000000000

**Logging JSON sections**: 
* di (Deal Info), ci (CPA Info), ct (CPA Tiers), ri (Revenue Info), rt (Revenue Tiers)
* Insert: @NewData only
* Update: @OldData + @NewData
* Delete: @OldData only

**Permission**: All mutation SPs call Aff_Con_CheckPermission with @FuncName='[Deal]'

**Timezone Normalization**: @CurrentDate = DATEADD(HOUR,12,GETDATE()) then CAST(@CurrentDate AS DATE)

## Aff_Admin_Deal_Ins

**PURPOSE**: Create a new deal (Revenue Share / CPA / Hybrid) with validation, tier configuration, CPA versioning, billing schedule initialization, and audit logging.

**BUSINESS RULE**: Deal creation requires unique name, valid tier configuration (Revenue: sequential MinNetWin; CPA: at least one threshold per tier), permission check, and automatic versioning for CPA settings (FromDate=ActionDate, ToDate=9999-12-31).

**PARAMETERS**:

| @UserId | INT | Yes | - | User performing action (permission check) |
| @GroupId | INT | No | OUTPUT | Assigned SCOPE_IDENTITY after insert |
| @GroupName | NVARCHAR(100) | Yes | - | Deal name (must be unique) |
| @GroupTypeId | INT | Yes | - | Deal type (1=Revenue, 3=CPA, 4=Hybrid) |
| @SubCommRate | DECIMAL(9,8) | No | NULL | Sub-commission rate (required if @IsSubCommRate=1) |

**LOGIC FLOW**:

```sql
1. Permission check (Aff_Con_CheckPermission '[Deal]')
2. Validate basic inputs (name, sub-commission)
3. Parse & validate Revenue tiers/deductions (if type 1/4)
4. Parse & validate CPA tiers/products/group settings (if type 3/4)
5. INSERT CommGroup; capture @GroupId (SCOPE_IDENTITY())
6. INSERT CommGroupHistory snapshot
7. INSERT Revenue TierSetting/DeductionSetting (+History) if applicable
8. INSERT CPAGroupSetting, CPATierSetting, CPAProductSetting if applicable
9. Compute NextBillingDate (monthly: EOMONTH(@StartDate, IntervalValue-1) + 4 days; else date arithmetic)
10. INSERT DealBillingSchedule (CPA/Hybrid)
11. Build JSON (@NewData) with di/ri/rt/ci/ct sections
12. Write audit log (Aff_UserLog_RunSP_Detail_WriteLog)
13. Return @ErrCode=0, @ErrMsg='Success'
```

**DECISION TREE**:

```text
Permission? → Fail → Abort
  Pass → Deal Type Revenue/Hybrid? → Yes → Validate Revenue tiers/deductions
  Deal Type CPA/Hybrid? → Yes → Validate CPA tiers/products/group settings
All validations pass? → No → Abort with ErrCode
INSERT CommGroup → SCOPE_IDENTITY() set? → No → Err 105
Write dependent config rows (revenue &/or CPA) → Build schedule → Log → Success
```

**SIDE EFFECTS**:

* Creates multiple versioned rows (CPA) with open-ended ToDate=9999-12-31.
* Schedule initialization influences downstream payment cadence.
* Audit JSON snapshot for full reproducibility.

**EDGE CASES**:

* Duplicate name prevented early (Err 102).
* Empty CPA tier list blocked (Err 302) while empty revenue tiers allowed.
* Max tiers enforced uniformly (Err 103).
* MinTO provided without products triggers validation failure.
* Quota=0 denotes unlimited quota.
* HoldingTickets=0 allowed (no holding requirement).

**IDEMPOTENT**: No (produces a new deal record each execution; duplicates blocked by name uniqueness).

**PERFORMANCE NOTES**:

* Light insert workload (<100 rows typical).
* XML parsing cost negligible at <=50 tiers.
* Index reliance on CommGroup.GroupName for uniqueness.

**SAMPLE I/O**:

* Valid CPA deal → Inserts CommGroup + CPA settings + schedule; @ErrCode=0.
* Duplicate name → @ErrCode=102, no inserts.
* CPA tier missing thresholds → @ErrCode=309, abort.

**DEPENDENCIES**:

- Calls: Aff_Con_CheckPermission, Aff_f_GroupProduct, Aff_UserLog_RunSP_Detail_WriteLog
- Requires: GroupType, Schedule, Product reference data.

**BUSINESS RULE**: Name uniqueness enforced; permission required; revenue tier and CPA tier/product rules re-validated; CPA-related changes generate new version rows only if any tracked CPA attribute differs; same-day CPA changes delete old open row instead of creating overlapping date ranges; otherwise previous open rows closed (ToDate = ActionDate - 1) then new open row inserted (ToDate=9999-12-31).

**LOGIC FLOW**:

```sql
1  Permission check
2  Load existing deal (GroupTypeId, ScheduleId, StartDate)
3  Validate base fields (name, sub-commission, uniqueness)
4  If Revenue/Hybrid: parse XML -> build @DeductionSetting, @TierSetting -> compute MaxAmount -> validate sequences
5  If CPA/Hybrid: parse CPATier/Product lists -> derive Max ranges -> validate thresholds & uniqueness
6  Update CommGroup (conditional columns by type)
7  Replace CommGroupHistory row for @MonthDate
8  Revenue/Hybrid: delete + reinsert TierSetting & DeductionSetting (+ history)
9  CPA/Hybrid: detect changes vs current open rows
  a. Same-day change? Delete existing open rows; else close with ToDate=ActionDate-1
  b. Insert new version rows for CPAGroupSetting, CPATierSetting, CPAProductSetting
10 Compose JSON old/new (di, ri, rt, ci, ct) using staged old data (#updateData & @old_* tables)
11 Write audit log
12 Success -> ErrCode=0
```

**DECISION TREE**:

```text
Permission OK? → No: abort
Deal exists? → No: Err 100
Name valid & unique? → No: Err (101/102)
Deal type includes Revenue? → Yes → Validate & replace tiers/deductions
Deal type includes CPA? → Yes → Validate & version CPA settings
CPA settings changed? → Yes → Version rows (same-day delete vs close-and-insert)
All validations pass → Apply updates → Log → Success
```

**SIDE EFFECTS**:

- Historical CPA versioning creates audit trail of configuration evolution.
- Monthly CommGroupHistory snapshot overwritten for current EOM.
- UserLog holds granular JSON diff enabling rollback analysis.

**EDGE CASES**:

- Same-day CPA changes avoid redundant closing row by DELETE then INSERT.
- No CPA changes → existing open CPA rows retained (no new version inserted).
- Tier / deduction XML missing (Revenue type) leads to existing settings being fully purged & replaced by new parsed sets (can be empty). 
- MinTO presence demands CPAProductList.

**IDEMPOTENT**: No — repeated execution with identical inputs still updates timestamps & may rewrite history rows (and log again), though CPA version rows only added if a diff is detected.

**ERRORS**:

| Code | Meaning |
|------|---------|
| 0 | Success |
| 100..316 | As defined in error code map (validation failure) |
| propagated | Permission failure or internal parsing error |

**PERFORMANCE NOTES**:

- XML parsing dominates for large product lists (bounded by <=50 tiers).
- Set-based deletes then inserts (no row-by-row updates) simplify maintenance.
- Version detection uses FULL OUTER JOIN and diff comparisons; ensure indexes on CPA*Setting(GroupId,ToDate).

**SAMPLE I/O**:

- Change only description (CPA unchanged) → CommGroup updated; no new CPA version rows; log captures old/new di.
- Adjust ActiveDays (CPA) → Old CPAGroupSetting closed or deleted (same-day), new row inserted; CPATier/Product untouched if unchanged.
- Add new CPA tier → CPATierSetting versioned; Product unchanged; log includes ct diff.

**DEPENDENCIES**:

- Aff_Con_CheckPermission, Aff_f_GetMessageById, Aff_f_AddRelatedProducts
- Aff_UserLog_RunSP_Detail_WriteLog (audit)
- string_split (product ID parsing)
- Products, Schedule reference data.

### Aff_Admin_Deal_Del

PURPOSE: Mutation – soft delete a deal by setting CommGroup.IsDeleted=1 and writing a JSON snapshot (old data only) to user log.

BUSINESS RULE:

* Permission required '[Deal]'.
* Cannot delete if any affiliate currently assigned (AffInfo.GroupId = target).
* Captures comprehensive OLD JSON sections (di, ri, rt, ci, ct) reflecting current configuration before deletion.
* Leaves historical version rows intact.

PARAMETERS: @UserId, @GroupId, @IP, @ErrCode OUTPUT, @ErrMsg OUTPUT.

DERIVED VALUES: @CurrentDate (timezone +12h), @ActionDate, @Duration for logging.

READS FROM: CommGroup, DeductionSetting, TierSetting, CPATierSetting, CPAProductSetting, Products, Schedule, AffInfo (usage check), Aff_Con_CheckPermission.

WRITES TO: CommGroup (IsDeleted=1), UserLog.

VALIDATION RULES:

* Permission failure -> abort.
* Group existence -> ErrCode 101 variant (message id 1006 maps to not existed).
* Group in use (AffInfo exists) -> ErrCode 102 (message id 1008 cannot delete).

LOGIC FLOW:

1. Permission check.
2. Existence + usage validation.
3. UPDATE CommGroup IsDeleted=1 (ROWLOCK, UPDLOCK).
4. Build JSON parts: DealInfo, RevenueShareInfo, TierJson, CPAInfo, CPATierJson (conditional by GroupType 1/3/4).
5. Compose @OldData with only old sections.
6. Write log (Aff_UserLog_RunSP_Detail_WriteLog) – no @NewData.

SIDE EFFECTS: Deal hidden from future selection; existing affiliate history unaffected.

EDGE CASES: Revenue-only deal → CPA sections empty objects; CPA-only deal → revenue sections empty.

IDEMPOTENT: No (second call returns usage error or does nothing if already deleted; no repeated logging of same snapshot unless undone externally).

PERFORMANCE NOTES: Lightweight; JSON composition queries can be optimized via narrower selects if needed.

### Aff_Admin_Assign_Deal

PURPOSE: Operation – assigns a commission group (deal) to an affiliate, maintaining history versioning (AffGroupHistory) and audit logging of old vs new assignment. (Header metadata sets isNested="1" indicating internal helper characteristics though callable by admin layer.)

BUSINESS RULE:

* Permission required '[Deal]'.
* If new GroupId same as existing -> early return (no log).
* Same-day multiple changes: previous history row for that day deleted to consolidate; otherwise prior open row closed (ToDate & MonthDate set to ActionDate-1) then new open row inserted.
* Logs da (Deal Assignment) old/new JSON objects including group name, type, action date.

PARAMETERS: @UserId, @AffId, @GroupId, @IP, @ErrCode OUTPUT, @ErrMsg OUTPUT.

DERIVED: @CurrentDate, @ActionDate, @MonthDate (last day of current month), @ParentAffId, @AllParentAffId, @OldGroupId, @OldActionDate.

READS FROM: AffInfo (current group, hierarchy), CommGroup (new & old names/types), AffGroupHistory (existing open rows), GroupType (names), Aff_Con_CheckPermission.

WRITES TO:

* AffInfo (UPDATE GroupId)
* AffGroupHistory (DELETE same-day rows; UPDATE close old; INSERT new)
* UserLog (audit old/new da JSON)

VALIDATION RULES:

* Permission failure aborts.
* New GroupId must exist and not IsDeleted (ErrCode 100 if invalid).
* No change (same group) returns without logging.

LOGIC FLOW:

1. Permission check.
2. Validate @GroupId exists & active.
3. Load current affiliate group context.
4. Early exit if unchanged.
5. Normalize dates; assign AffInfo.GroupId.
6. Delete same-day history row if exists.
7. Close previous open row if exists (ToDate / MonthDate set to ActionDate-1).
8. Insert new AffGroupHistory row (open ToDate=9999-12-31).
9. Build old/new da JSON; write log.

SIDE EFFECTS: Modifies current affiliate deal and historical lineage.

EDGE CASES: Multiple changes within same day collapse to single history row reflecting latest assignment. MonthDate stored as the month-end date of the current action month (not previous month end).

IDEMPOTENT: No (repeated different assignments mutate history each time; same assignment short-circuits).

PERFORMANCE NOTES: Minimal writes (1–3 history row ops). Ensure AffGroupHistory indexed on AffId, MonthDate, ToDate.

SAMPLE I/O: Assign AffId=500 from GroupId=10 to 12 same day twice → final single history row FromDate=ActionDate, previous closed row ToDate=ActionDate-1.

DEPENDENCIES: Aff_Con_CheckPermission, Aff_UserLog_RunSP_Detail_WriteLog.
